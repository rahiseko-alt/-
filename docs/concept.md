# AI支援型DTP制作システム 構想説明

## 1. 目的

本プロジェクトは、パンフレット、募集要項、チラシ、ポスター等の複数の冊子・紙面（以下「BOOK」）を、複数の参考資料から分析・再構成し、最終的に自社（AIビジネス専門学校）の情報へ差し替えて制作・更新できる仕組みを構築することを目的とする。

単発で1冊を作るのではなく、今後複数のBOOKを継続的に制作・修正できる「AI支援型DTP制作基盤」とする。

---

## 2. 基本方針

このシステムでは、1つの巨大なモノレポを制作の正本とする。

モノレポ内に以下を集約する。

- 制作ルール
- 開発環境
- 自社の正本データ
- 他社・他校の参考資料
- 各BOOKの制作データ
- 共通コンポーネント
- 画像生成物
- レビュー結果
- 出力物

会社やBOOKごとに環境を複製しない。

自社情報は1か所だけに保持し、パンフレット、募集要項、チラシ等から共通参照する。

## 4. 自社データの考え方

`company-data/` を自社情報の唯一の正本とする。

例：

```text
company-data/
├─ brand/
│  ├─ logo/
│  ├─ colors/
│  └─ fonts/
│
├─ facts/
│  ├─ school.yaml
│  ├─ courses.yaml
│  ├─ teachers.yaml
│  ├─ results.yaml
│  └─ contacts.yaml
│
├─ photos/
└─ copy/
```

学校名、住所、電話番号、学科、教員、実績、ブランドカラー等をBOOKごとに重複保存しない。

変更が発生した場合は原則として `company-data/` の正本を更新し、各BOOKがそれを参照する。

---

## 5. 参考資料の考え方

他社・他校のパンフレット、募集要項、チラシ等はすべて `references/` に集約する。

BOOKごとに参考資料をコピーしない。

各BOOK側では「どの参考資料を使うか」だけを指定する。

例：

```yaml
references:
  - references/HAL/brochure/
  - references/A-school/brochure/
  - references/B-school/brochure/
```

必要に応じてページ単位でも参照先を指定する。

例：

```yaml
page_016:
  layout_reference:
    - references/HAL/brochure/page_016.png

  visual_reference:
    - references/A-school/brochure/page_031.png

  information_reference:
    - references/B-school/brochure/page_008.png
```

この設計により、

- レイアウトはHAL
- 写真の見せ方はA校
- 数字の見せ方はB校
- 掲載内容は自社データ

のような組み合わせが可能になる。

---

## 6. BOOKの考え方

BOOKは実際に制作する成果物単位とする。

例：

```text
books/
├─ brochure/
├─ admissions/
├─ flyers/
│  ├─ open-campus/
│  ├─ recruitment/
│  └─ ...
└─ ...
```

各BOOKは以下を持つ。

```text
books/brochure/
├─ config/
├─ references.yaml
├─ backgrounds/
├─ pages/
├─ reviews/
└─ output/
```

BOOKごとに独自のデザインルールやページ構造を持たせるが、共通データや共通部品は中央から参照する。

---

## 7. ページ制作の基本設計

最終ページは「1枚の画像だけ」で作らない。

以下の3層構造を基本とする。

### Layer 1：BASE VISUAL

AI画像生成を活用する。

対象：

- 背景
- 写真
- 生成ビジュアル
- グラデーション
- 光
- テクスチャ
- 複雑な装飾
- 写真と背景の融合表現

画像生成の表現力を利用し、誌面全体の質感・密度・完成度を担保する。

### Layer 2：STRUCTURE

HTML / CSS / SVGで描画する。

対象：

- カード
- 枠
- 罫線
- 半透明パネル
- 単純図形
- マスク
- 色面
- 本文量に応じてサイズが変わる領域

文章量やレイアウト変更に追従させる必要がある要素は背景画像へ焼き込まない。

### Layer 3：CONTENT

HTML等で正確に配置する。

対象：

- 見出し
- 本文
- 数字
- 学科名
- 氏名
- 企業名
- URL
- ページ番号
- QRコード
- キャプション

文字は画像生成へ任せず、コードで座標・サイズ・行間を調整する。

---

## 8. この3層構造を採用する理由

画像生成だけの場合、

- 日本語本文が壊れる
- 数字が変わる
- 固有名詞を誤る
- 修正のたびに再生成が必要
- 指定していない部分まで変化する

という問題がある。

逆にHTML/CSS/SVGだけでは、

- 薄い背景装飾
- 光
- テクスチャ
- 複雑な写真合成
- 雑誌的な質感

が弱くなりやすい。

そのため、

**表現力は画像生成、正確性はコード**

という役割分担を採用する。

## 9. 制作フェーズ

### Phase 1：基礎環境構築

最初に1回だけ、制作基盤を作る。

構築対象：

- GitHubモノレポ
- Dev Container
- Node.js / TypeScript
- Vite
- Playwright / Chromium
- 画像処理
- PNG/PDFレンダリング
- 日本語フォント
- 共通スクリプト
- AGENTS.md
- CLAUDE.md
- ルール管理
- データ形式
- ディレクトリ構成

この段階では本格的なBOOK制作を始めない。

### Phase 2：環境をテンプレート化

基礎環境完成後、以降すべてのBOOK制作に共通利用できる制作基盤として固定する。

ただし、会社ごとにリポジトリを複製するのではなく、同一モノレポ内へBOOKと参考資料を追加していく。

### Phase 3：参考資料投入

パンフレット、募集要項、チラシ等の参考資料をBOOK種別ごとに整理して `references/` へ格納する。

PDFだけでなく、ページ単位のPNG/JPGも保存する。

AIはOCR結果だけで判断せず、参考ページ画像を実際に視覚確認する。

### Phase 4：参考資料解析

参考資料から以下を抽出する。

- グリッド
- 余白
- ガター
- 写真比率
- 見出し階層
- 色
- 罫線
- カード
- 情報密度
- ページタイプ
- 視線誘導
- 背景表現
- 画像クロップ
- ページ間のリズム

分析結果はファイルとして保存し、会話履歴だけに残さない。

### Phase 5：完コピ検証

代表ページをまず高精度に再現する。

目的はコピーそのものではなく、参考デザインを正しく構造化できているかの確認。

流れ：

```text
参考画像確認
↓
背景画像生成
↓
HTML/CSS/SVG実装
↓
テキスト配置
↓
PNGレンダリング
↓
元画像との比較
↓
修正
```

最低2回は視覚比較と修正を行う。

### Phase 6：BASELINE確定

再現方式が安定した後、基準版を `baseline` として確定する。

この段階で初めて保護機構を導入する。

### Phase 7：保護機構

確定した基準データは、AIの誤操作で変更されないよう保護する。

想定する多層防御：

1. Filesystem Permission
2. PreToolUse Hook
3. Git差分チェック / CI

例：

```text
system/rules/       READ ONLY
references/         READ ONLY
baseline/           READ ONLY
company-data/       WRITE
books/              WRITE
shared/             WRITE
```

baselineの修正が必要な場合のみ、専用のメンテナンス権限を使う。

### Phase 8：自社版への変換

参考資料の固有情報をコピーせず、レイアウト・情報設計・デザイン構造だけを利用してAIビジネス専門学校版へ変換する。

使用する自社情報は `company-data/` のみとする。

参考資料から以下を流用しない。

- 学校名
- 実績
- 数字
- 人物
- 企業名
- ロゴ
- 学科名
- インタビュー
- 写真
- 固有コピー

### Phase 9：日常編集

初期制作が終わったBOOKについては、毎回ゼロからデザインしない。

日常作業は主に以下とする。

- 文章変更
- 数字変更
- 写真差し替え
- 背景差し替え
- 見出し位置調整
- 文字サイズ調整
- 行間調整
- 色変更
- ページ追加
- ページ削除
- PNG/PDF再出力

デザインを「再生成するもの」ではなく「資産」として扱う。

## 10. AIの役割分担

### Claude Code

主に以下を担当する。

- 初期リポジトリ構築
- Dev Container
- ディレクトリ設計
- ルール整備
- データ構造
- HTML/CSS/SVG実装
- 継続的なコード修正

### Codex

主に以下を担当する。

- 参考画像分析
- 背景画像・キービジュアル生成
- 画像生成プロンプト管理
- HTML/CSS/SVG実装
- コード修正
- 視覚レビュー

### 原則

Claude CodeかCodexかに依存する設計にはしない。

どちらを使用しても、

- 同じルール
- 同じリポジトリ
- 同じデータ
- 同じレンダリング
- 同じテスト
- 同じレビュー基準

で作業できる状態を目指す。

---

## 11. GitHub運用

GitHubを唯一の正本とする。

毎回新しいPC、新しいCodex/Claude Codeセッション、新しいコンテナから作業を開始できることを前提とする。

会話履歴に依存しない。

基本フロー：

```text
GitHub最新状態取得
↓
新規コンテナ
↓
AGENTS.md / CLAUDE.md確認
↓
対象BOOK確認
↓
作業
↓
render / test
↓
commit
↓
push
↓
セッション終了
```

「セッションを継続する」のではなく、「GitHubを継続する」。

---

## 12. 大容量参考資料

参考資料のPNG、JPG、PDFは容量が大きくなるため、原則としてGit LFSを利用する。

対象例：

```text
*.png
*.jpg
*.jpeg
*.pdf
```

規模が大きくなった場合は、将来的に `references/` のみ外部ストレージへ分離することも検討する。

初期段階では、

**1モノレポ + Git LFS**

で開始する。

---

## 13. 将来像

本システムは単なるパンフレット作成環境ではない。

最終的には、

- パンフレット
- 募集要項
- チラシ
- ポスター
- 学校案内
- イベント告知
- その他紙媒体

を、複数の参考資料から設計分析し、自社情報を使って制作・更新できる「AI支援型DTP制作システム」とする。

基本思想は以下。

```text
複数の参考資料
      ↓
デザイン構造を分析
      ↓
背景・ビジュアルをAI生成
      ↓
構造をHTML/CSS/SVGで制御
      ↓
自社の正本データを配置
      ↓
PNG / PDFとして出力
      ↓
デザインを資産化
      ↓
以後は差し替え・微調整で運用
```

---

## 14. 最重要原則

1. GitHubを唯一の正本にする
2. 自社データは1か所だけに持つ
3. 参考資料と自社情報を混同しない
4. 画像生成に文字の正確性を求めない
5. コードだけで全デザインを描こうとしない
6. 背景画像・構造・テキストを分離する
7. 初期制作と日常編集を分ける
8. AIの会話履歴ではなくファイルに状態を残す
9. 確定データは技術的に保護する
10. 一度作ったデザインを再利用可能な資産にする
